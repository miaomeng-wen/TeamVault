# 团队知识库建设方案

> 本文档是只读设计文档：记录这套体系"为什么长这样"。要改设计，先在团队会上提出，修订本文并同步修订 [[../AGENTS|AGENTS.md]]。

## 一、一句话结论

**Obsidian vault 管知识，Git 管协作与历史，团队文件库管 PDF 与数据，智能体管录入、质检与摘要，Dataview 管派生视图** —— 核心资料使用开放格式，不依赖专用文献管理平台。

## 二、现状诊断

本方案以一份来源一篇 Markdown 笔记为基础，来源信息、阅读状态和团队提炼集中在同一处：

- **幂等写入**：按 `source_id` 全库查重，重复录入只补全原笔记。
- **双状态机**：`reading_status` 与 `screening_status` 让进度可审计、可派生。
- **页码级证据**：关键结论记录页码并链接 `pdf_url` 或 `source_url`，未核验内容不补造。
- **文件外置**：PDF、数据集等大文件由团队文件库存储，Git 只保存 Markdown 和小型附件。

团队知识库常见的四个障碍，本方案逐一拆除：

| 障碍      | 个人版                                | 团队版对策                                     |
| ------- | ---------------------------------- | ----------------------------------------- |
| 无版本控制   | vault 不在 Git 里                     | vault 整体入库，历史/回滚/审计齐全                     |
| 来源信息分散  | 元数据、PDF、阅读笔记各存一处                   | 文献笔记 frontmatter 作为来源身份与状态事实源，PDF 用稳定链接关联 |
| 热点冲突文件  | `当前进度.md`、`00_待读文献.md` 等单文件多人并发写必炸 | 状态进 frontmatter，看板全部 Dataview 派生，无手工总表    |
| 大文件拖慢仓库 | PDF、数据集直接进 Git                     | 大文件进入团队文件库，vault 仅保存链接                    |

## 三、五层架构

```
┌─ 视图层  04_Tables 派生看板（任务看板/文献索引/待读清单）         禁止手改
├─ 知识层  02_Literature 等笔记正文 + frontmatter（状态即事实）   认领制写入
├─ 规范层  AGENTS.md 宪法 + 07_Templates 模板 + CONTRIBUTING    团队决议修订
├─ 资料层  团队文件库（PDF / 数据集 / 大型附件）                   权限控制 + 独立备份
└─ 协作层  Git 私有仓库（历史 / 回滚 / 冲突合并 / 审计）           主干式小提交
          智能体横跨各层：录入(intake) → 写入(模板) → 质检(qa) → 摘要(digest)
```

## 四、关键决策与理由

**1. 知识事实源使用 Markdown。**
来源元数据、状态、摘要和证据都进入文献笔记；`source_id` 优先采用 DOI，无 DOI 时使用规范化 URL 或 UUID。这样数据可读、可迁移，也便于脚本查重和质检。

**2. Git 只同步知识，不同步大文件。**
Git 负责可审计历史、回滚和冲突合并；PDF、数据集进入团队文件库。两层通过 `source_url` 与 `pdf_url` 连接，避免仓库因二进制文件持续膨胀。

**3. 热点文件去中心化：状态进 frontmatter，视图靠派生。**
"谁认领哪篇、读到哪了"写在每篇笔记的 `assignee` / `reading_status` 字段里，任务看板、待读清单全部由 Dataview 查询生成。没有总表可冲突，也就没有并发写问题；代价是放弃"打开一个文件看全部"，换来零维护成本。

**4. 主干式协作 + 认领制，不做 feature 分支。**
Markdown 笔记的合并成本远低于分支管理成本。冲突防护靠三件事：认领制（一篇笔记只有一个写入者）、按 `source_id` 幂等查重、热点去中心化。Git 只做兜底。

## 五、实施路线

| 阶段 | 内容 | 执行者 | 状态 |
| --- | --- | --- | --- |
| 0. 骨架 | 目录结构、规范、模板、派生看板、Git 初始化 | 管理员 | ✅ |
| 1. 文件层 | 选定团队文件库，确定目录、权限、稳定链接和备份负责人 | 管理员 + 团队 | ⬜ |
| 2. 团队管线 | 安装 `team-skills`；试运行 source-intake → 写第一篇笔记 → vault-qa 自检 | 各成员 | ⬜ |
| 3. 远程与同步 | 建远程私有仓库、全员 clone、装 Obsidian Git 插件自动同步 | 管理员 + 成员 | ⬜ |
| 4. 服务化 | `team-digest` 周报定时化；vault-qa 接入定期巡检 | 各成员 agent | ⬜ |
| 5. 扩展 | 组会纪要流程、实验记录规范、概念词典自动抽取 | 按需 | ⬜ |

## 六、智能体分工

| 技能 | 职责 | 输入 | 输出 | 边界 |
| --- | --- | --- | --- | --- |
| `source-intake` | 整理并查重来源 | DOI / URL / PDF 链接 / 元数据 | 02_Literature 笔记 | 不上传或移动外部文件 |
| `vault-qa` | 规范巡检 | 全库扫描 | 质检报告 | 只报告，不擅改 |
| `team-digest` | 周报 | 时间窗 + git log | 08_Daily 周报 | 只写 08_Daily |
| 检索问答 | 回答团队问题 | 自然语言问题 | 带出处的回答 | 引用必须给笔记链接 |

## 七、风险与对策

- **外部链接失效**：团队文件库必须使用稳定链接；周报或 QA 定期曝光缺失链接，迁移文件库时统一维护链接。
- **文件库不可用**：指定备份负责人，保留版本或快照，并定期抽查恢复能力。
- **隐私边界**：私有仓库全员可见全部笔记。个人草稿、评审中的敏感材料留在仓库外的本地目录。
- **Git 门槛**：非技术成员只依赖 Obsidian Git 插件自动化 + "常见问题"速查；出问题管理员兜底。
- **派生看板信任度**：看板完全依赖 frontmatter 纪律。对策：vault-qa 定期巡检缺字段/非法状态，team-digest 周报曝光积压。
- **访问令牌泄露**：`.env` 已 ignore；泄露后立即在对应服务撤销重建。
