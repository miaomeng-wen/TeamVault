# 团队知识库建设方案

> 本文档是只读设计文档：记录这套体系"为什么长这样"。要改设计，先在团队会上提出，修订本文并同步修订 [[../AGENTS|AGENTS.md]]。

## 一、一句话结论

**Zotero 群组库管"书"，Obsidian vault 管"笔记"，Git 管"协作与历史"，智能体管"搬运、质检与摘要"，Dataview 管"派生视图"** —— 五层各司其职，互不越界。

## 二、现状诊断

这套设计沿用并团队化了一套已在个人环境验证过的管线（Zotero 本地库 → 只读抓取 → 中文文献笔记 → Dataview 索引 → 检索问答），其优势直接继承：

- **幂等写入**：按 `item_key` 全库查重，重复生成不产生副本——多人并发写天然安全。
- **双状态机**：`reading_status`（unread/reading/finished/excluded）与 `screening_status`（included/candidate/excluded）让进度可审计、可派生。
- **页码级证据**：`zotero://open-pdf/...?page=N` 跳转 + "未核验不补造"规则，保证笔记可信。
- **队列与目录解耦**：Zotero collection 只当处理队列，笔记按主要贡献归档，避免结构随分类漂移。

个人方案团队化时暴露的四个障碍，本方案逐一拆除：

| 障碍 | 个人版 | 团队版对策 |
| --- | --- | --- |
| 无版本控制 | vault 不在 Git 里 | vault 整体入库，历史/回滚/审计齐全 |
| 文献源单机 | 本地私有 Zotero 库，Local API 只限 127.0.0.1 | Zotero 群组库（Group Library）作为团队书目事实源 |
| 热点冲突文件 | `当前进度.md`、`00_待读文献.md` 等单文件多人并发写必炸 | 状态进 frontmatter，看板全部 Dataview 派生，无手工总表 |
| 环境硬编码 | vault 路径、skill 路径写死在脚本里 | 路径与密钥走 `config/.env` 与环境变量 |

## 三、五层架构

```
┌─ 视图层  04_Tables 派生看板（任务看板/文献索引/待读清单）      禁止手改
├─ 知识层  02_Literature 等笔记正文 + frontmatter（状态即事实）  认领制写入
├─ 规范层  AGENTS.md 宪法 + 07_Templates 模板 + CONTRIBUTING    团队决议修订
├─ 文献源  Zotero 群组库（元数据 + PDF）                        对脚本只读
└─ 共享层  Git 私有仓库（历史 / 回滚 / 冲突合并 / 审计）        主干式小提交
          智能体横跨各层：抓取(fetcher) → 写入(模板) → 质检(qa) → 摘要(digest)
```

## 四、关键决策与理由

**1. 同步用 Git，不用 Syncthing / Obsidian Sync。**
智能体工作流需要：可审计历史（谁改了什么）、可回滚、冲突可合并、脚本可挂质检。只有 Git 全部满足。成员门槛用 Obsidian Git 插件定时自动 pull/push 消解；对智能体则零门槛（本来就是它的主场）。

**2. 文献源用 Zotero 群组库，不共享本地库。**
`zotero.sqlite` 是单机文件且禁止并发写，任何"共享文件夹里的 Zotero"方案都会损坏数据。群组库是官方多人方案：每人本地 Zotero 同步同一个群组，元数据与 PDF 都在；脚本经 Web API（配只读 Key）访问，本地 API 仅作离线兜底。

**3. 热点文件去中心化：状态进 frontmatter，视图靠派生。**
"谁认领哪篇、读到哪了"写在每篇笔记的 `assignee` / `reading_status` 字段里，任务看板、待读清单全部由 Dataview 查询生成。没有总表可冲突，也就没有并发写问题；代价是放弃"打开一个文件看全部"，换来零维护成本。

**4. 主干式协作 + 认领制，不做 feature 分支。**
Markdown 笔记的合并成本远低于分支管理成本。冲突防护靠三件事：认领制（一篇笔记只有一个写入者）、幂等查重（同 key 只更新）、热点去中心化（没有共享可写文件）。Git 只做兜底。

## 六、智能体分工

| 技能 | 职责 | 输入 | 输出 | 边界 |
| --- | --- | --- | --- | --- |
| `zotero-team-fetcher` | 抓群组库条目/分类/附件 | item key / collection | JSON | Zotero 只读 |
| 文献笔记生成 | 模板 + fetcher 数据 → 笔记 | 单条条目 | 02_Literature 笔记 | 认领制 + 幂等查重 |
| `vault-qa` | 规范巡检 | 全库扫描 | 质检报告 | 只报告，不擅改 |
| `team-digest` | 周报 | 时间窗 + git log | 08_Daily 周报 | 只写 08_Daily |
| 检索问答 | 回答团队问题 | 自然语言问题 | 带出处的回答 | 引用必须给笔记链接 |

## 七、风险与对策

- **PDF 存储配额**：Zotero 免费版群组库 300MB。对策：大 PDF 走团队网盘/NAS，群组库留元数据；或升级 Zotero Storage（$20/年起 2GB）。
- **隐私边界**：私有仓库全员可见全部笔记。个人草稿、评审中的敏感材料留在仓库外的本地目录。
- **Git 门槛**：非技术成员只依赖 Obsidian Git 插件自动化 + "常见问题"速查；出问题管理员兜底。
- **派生看板信任度**：看板完全依赖 frontmatter 纪律。对策：vault-qa 定期巡检缺字段/非法状态，team-digest 周报曝光积压。
- **Key 泄露**：`.env` 已 ignore；泄露立即在 zotero.org 撤销重建（Key 只读权限，损失可控）。
