## 一、开场：团队知识库的四个典型障碍（1.5 min）

**讲法**：先问一句"我们现在文献都存在哪？"——微信群、各人电脑、Zotero、网盘大概率都有。然后给这张表。

| 障碍 | 常见现状 | 本方案对策 |
| --- | --- | --- |
| 无版本控制 | vault 不在 Git 里，改坏了回不去 | vault 整体入库，历史/回滚/审计齐全 |
| 来源信息分散 | 元数据、PDF、阅读笔记各存一处 | 文献笔记 frontmatter 作唯一事实源，PDF 用稳定链接关联 |
| 热点冲突文件 | `当前进度.md`、`待读文献.md` 多人并发写必炸 | 状态进 frontmatter，看板全部派生，**无手工总表** |
| 大文件拖慢仓库 | PDF、数据集直接进 Git | 大文件进团队文件库，vault 只存链接 |

## 二、架构与设计（4 min）

**一句话定位**（照念）：

> Obsidian vault 管知识，Git 管协作与历史，团队文件库管 PDF 与数据，智能体管录入/质检/摘要，Dataview 管派生视图。核心资料全部用开放格式，不绑定 Zotero 等专用平台。

**五层架构**：视图层 `04_Tables` → 知识层 `02_Literature` → 规范层 `AGENTS.md`+模板 → 资料层 团队文件库 → 协作层 Git。智能体横跨各层：录入 → 写入 → 质检 → 摘要。

**重点只讲一条决策**（其余留问答）：

> "状态进 frontmatter，视图靠派生"——传统团队库炸在 `当前进度.md` 这种热点文件上。我们的对策是**根本不设这个文件**：谁认领哪篇、读到哪了，全写在每篇笔记的 `assignee` / `reading_status` 字段里，任务看板、待读清单全部由 Dataview 查询实时生成。
> 代价是放弃"打开一个文件看全部"，换来的是**零维护成本 + 零并发冲突**。

**配套三条铁律**：来源即笔记 · 文件外置 · 认领制写入。

## 三、现场演示脚本（4 min）

按顺序走，每步一句话说明，不要停留太久：

1. **入口**：打开 `00_Home/Home.md` —— "全库入口，三条看板 + 五个主题目录"。
2. **派生看板**：打开 `04_Tables/团队任务看板.md` —— "注意页头写着'禁止手工编辑'。它下面全是查询语句，数据来自笔记本身"。
3. **单篇笔记**：打开 `02_Literature/02_数据集与基准/Chen_2026_DeMamba_GenVideo_Benchmark.md` —— 重点展示三处：
   - frontmatter 的**双状态机**（`reading_status` + `screening_status`）；
   - `source_id: doi:10.1007/s11432-024-4894-0` —— 全库唯一、幂等的来源身份；
   - 文末**页码级证据表** —— "每条结论能追到第几页，未读到的写'未核验'，不补造"。
4. **质检**：终端执行
   ```bat
   python team-skills\vault-qa\scripts\vault_qa.py --vault E:\TeamVault
   ```
   预期输出：`扫描笔记：02_Literature 2 篇 · 03_Concepts 0 篇；问题：0 ERR / 0 WARN` → "只读巡检，不自动改，报告交给认领人"。
5. **提交规范**：`git log --oneline -15` —— 展示前缀分工（`spec:` 规范 / `notes:` 笔记 / `qa:` 质检 / `vault backup:` 机器同步）。

## 六、预设问答

| 可能被问 | 建议答法 |

| "内容太少了，才 2 篇？" | 这一阶段交付的是**可运转的骨架与规范**，不是文献量。骨架跑通后灌内容是线性的；现在 5 个主题目录已就位，缺的只是人力投入。 |

| "为什么不直接用 Zotero 群组库？" | 早期方案确实基于 Zotero（已归档在 `99_Archive`），后来改为开放来源架构：核心资料用 Markdown + DOI 标识，不依赖任何单一平台的账号、配额和导出格式，可迁移性更强。 |
| "看板数据会不会不准？" | 会——看板完全依赖 frontmatter 纪律。对策是 `vault-qa` 定期巡检 + `team-digest` 周报曝光缺字段和积压，而不是靠人自觉。 |
